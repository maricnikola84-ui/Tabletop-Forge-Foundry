# N5EB Automation Rules

These are the durable rules for automation work in this repository.

## 1. Source integrity first

- Use the installed/pinned N5EB 3.1.1 documents as the source of truth.
- Never invent a feat, clan feature, class feature, Jutsu, item, condition, advancement, rank, Chakra cost, or activity when the real document exists.
- Never rewrite official compendium source documents just to make automation easier.
- Runtime automation should work on actor-owned copies, Active Effects, enchantments, flags, or other reversible overlays.

## 2. Native mechanics before prose parsing

When a Jutsu or feature is used:

1. inspect its real N5EB activities and `activity.applicableEffects`;
2. use the native activity/effect if it deterministically represents the rule;
3. parse description text only for mechanics the document does not already express.

For N5EB 3.1.1, `dnd5e.postUseActivity` is the normal cast/use integration point used by our automation layer.

## 3. Do not fire hostile effects early

A hostile condition is not applied merely because a Jutsu contains that condition in its text/profile.

Wait for the actual trigger:

- successful hit;
- failed save;
- critical failure;
- damage actually resolving;
- another explicit rule trigger.

This prevents Fire/Acid/etc. from applying Burned/Corroded on cast and prevents Stunned/Slowed/etc. from being applied before a target fails the relevant roll.

## 4. Target-linked state must stay target-linked

Effects such as Pain, Doubled Pain, Unlimited Pain, marks, curses, or victim-specific bonus damage must store the affected target identity. Never implement these as a global caster buff that leaks into other targets in an AoE.

Damage hooks must evaluate the damaged actor/token individually.

## 5. Optional mechanics must prompt

Never silently:

- spend Chakra, Cursed Energy, Tenacity, reactions, limited uses, or other resources;
- select a Jutsu option;
- activate an optional feature;
- pick an affinity, save proficiency, manifestation, specialization, or similar player choice.

Deterministic mechanics can automate. Choices should be buttons/prompts/settings.

## 6. Multiple native effect profiles

If an activity has exactly one deterministic effect profile, it may be auto-applied when correct.

If it exposes several effect profiles representing a choice, leave the normal N5EB effect tray/choice flow in control unless a specific handler knows exactly which profile is valid. Never auto-apply every profile by default.

## 7. Concentration and duration

Concentration-linked buffs should depend on the real N5EB concentration Active Effect. Effects generated by automation should end when their real duration, concentration, rest recovery, or other rule says they end.

Do not create permanent hidden bonuses for temporary Jutsu.

## 8. Enchantment compatibility

N5EB 3.1.1 supports real enchantment effects on actor-owned Jutsu. Common supported fields include:

- `system.damage.bonus`
- `system.damage.parts`
- `system.attack.bonus`
- `system.save.dc`
- `system.chakra.cost`

Actor-level buffs should use the actual N5EB fields for AC, movement, saves, resistances, immunities, vulnerabilities, and flat Damage Reduction rather than fake text-only effects.

## 9. Generated state must be reversible

Every module-created effect or modified value should be identifiable by module flags. If automation temporarily replaces an authored value, snapshot the original value first.

Every major automation module should expose:

- audit/diagnostics;
- resync/rebuild;
- cleanup/rollback.

Cleanup must remove only module-created state, never upstream or manually-authored data.

## 10. Never double-apply authored mechanics

Before adding a bonus, inspect whether it is already baked into the actor, item, Active Effect, advancement, or custom sheet. Preserve authored values rather than stacking the same mechanic twice.

## 11. Resource pools

When a feature is represented by a real item-use pool, prefer the real pool (`system.uses.max`, `system.uses.spent`, recovery data) instead of creating a parallel hidden counter.

## 12. Conservative interpretation

If a mechanic is ambiguous, highly conditional, GM-discretionary, or depends on a missing choice/number, report it in the audit instead of guessing. Missing numbers are never invented.
